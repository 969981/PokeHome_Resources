# 一、结论与勘误

**不能把 `0x1D2FA20 BLR X8` 直接归于 `ApiManagerLogin.AtuhRegisterUser` 本体。**

之前使用的方法入口 `AtuhRegisterUser @ 0x1D2F8DC`，向后扫描
`0x200` 字节以找 `BLR`，范围跨过了相邻的代码段。新原版 AArch64 反汇编证明：

- `0x1D2F9E8 B 0x1D2F1F8`：前一段代码发生无条件尾跳转；
- `0x1D2F9F8 STP X30,X19,[SP,#-0x10]!`：随后出现新的函数栈帧序言；
- `0x1D2FA2C RET`：该相邻片段独立返回。

这三条机器码支持两段函数分界，但由于尚未从原版 ScriptMethod 中
精确关联 `0x1D2F9F8` 的官方方法名称，标记为
**UNCLASSIFIED_ADJACENT_CALLBACK**，不是已命名方法。

原版 APK SHA-256：
`8dee598028cd70441f645c8fff96b093b76778d625cdf07c60109eced50ffac1`

原版 `libil2cpp.so` SHA-256：
`80bfbc3d480bf3c91297d65a441a37e40260b70fd8b0ddc8da70c34f0870b6fe`

原版静态验收 [Home_Android Actions #42582396841](https://github.com/969981/Home_Android/actions/runs/42582396841) 已通过；所有地址按原版 ELF 的 RVA 使用，不是带 ASLR 的进程绝对地址。

# 二、相邻回调内部精确机器码

~~~asm
0x1D2F9F8  STP  X30,X19,[SP,#-0x10]!
0x1D2F9FC  CMP  W0,#0x190
0x1D2FA00  MOV  W8,#0x227F
0x1D2FA04  CCMP W1,W8,#0,EQ
0x1D2FA08  CSET W19,EQ
0x1D2FA0C  B.NE 0x1D2FA24
0x1D2FA10  CBZ  X3,0x1D2FA30
0x1D2FA14  LDR  X8,[X3,#0x18]
0x1D2FA18  LDR  X0,[X3,#0x40]
0x1D2FA1C  LDR  X1,[X3,#0x28]
0x1D2FA20  BLR  X8
0x1D2FA24  MOV  W0,W19
0x1D2FA28  LDP  X30,X19,[SP],#0x10
0x1D2FA2C  RET
~~~

原始字节由 `ci/home41_guest_native_static.py` 检查：
`0x190=400`，`0x227F=8831`。
可见一个条件门禁与 `X3` 回调对象非空检查；进入调用点时：

- `X8 = *(X3 + 0x18)`：间接被调用代码指针。
- `X0 = *(X3 + 0x40)`：第一个参数寄存器的来源。
- `X1 = *(X3 + 0x28)`：第二个参数寄存器的来源。

**绝不直接称 `W0=400` 为 HTTP 400，也不能称 `W1=8831` 为正式业务错误码**，除非后续真正找到此回调的调用者、参数枚举来源及服务端响应上下文。

# 三、主注册链与旁路回调分离

原版另一条静态链路由八条 A64 分支核验：

`ConfirmGestAccountSecond → 第二弹窗内部调用点 0x1DEB3C0 → 正向跳板 B 0x1DE5508 → DecisionGestAccount → B 0x1D2F8DC AtuhRegisterUser`。

请注意，第二弹窗中的委托对象在**实际运行时**是否确实选择正向跳板，仍需实机证明；同样，注册管理器入口与请求序列化之间是否属于同一个异步注册事务尚需闭合。

原生事件验收的推荐次序：

1. `firstboot_confirm_gest_second_entered`
2. `guest_second_decision_thunk_entered`
3. `firstboot_decision_gest_account_entered`
4. `auth_manager_register_user_entered`
5. `registration_request_serializer_entered`
6. `registration_response_handler_entered`
7. `token_response_handler_entered / login_response_handler_entered`
8. `first_basic_utid_observed`（公共 Basic 消费点已验证）

`nearby_conditional_callback_blr_entered` 是**旁路条件回调**，
即使它没有命中，也不能作为注册链失败的证据；
相反，单独命中它也不能证明账号注册成功。

# 六、继续闭合真实尾调用目标 0x1D2F1F8

[Home_Android Actions #42582858746](https://github.com/969981/Home_Android/actions/runs/42582858746)
和扩展后的 [#42582998714](https://github.com/969981/Home_Android/actions/runs/42582998714)
已用原版 SHA-256 锁定 ELF 进一步证实：

~~~asm
0x1D2F9C8  BL  0x1D2F584
0x1D2F9CC  MOV X0,X19
0x1D2F9E4  LDP X30,X27,[SP],#0x50
0x1D2F9E8  B   0x1D2F1F8
~~~

`0x1D2F1F8` 是与之前误认的 `0x1D2FA20` 完全不同的执行目标。
前者确实由 `AtuhRegisterUser` 的最后一段无条件尾跳转抵达。

扩展后的有限反汇编发现如下步骤：

| RVA | 原始指令 / 操作 | 保守解释 |
|---|---|---|
| `0x1D2F1F8` | `STR X30,[SP,#-0x40]!` | 新调用目标的函数序言 |
| `0x1D2F214` | `LDRB W8,[X19,#0x119]` | 读取静态初始化状态 |
| `0x1D2F220` | `TBNZ W8,#0,0x1D2F2A4` | 已初始化时跳过初始化区 |
| `0x1D2F29C` | `MOV W8,#1` | 更新静态初始化状态 |
| `0x1D2F2A4` | `LDR X0,[X22]` | 进入初始化后的主体 |
| `0x1D2F2D8` | `STURB W8,[X22,#-8]` | 存入布尔候选值 |
| `0x1D2F2F4` | `BL 0x1F27198` | 未分类的直接被调函数 |
| `0x1D2F324` | `BL 0x1D35CC8` | 待按原版方法索引命名的核心调用候选 |
| `0x1D2F384` | `BL 0x1D4BF14` | 未分类被调函数 |
| `0x1D2F38C` | `BL 0x1D656BC` | 未分类被调函数 |
| `0x1D2F3A4` | `BL 0x1D8AA54` | 未分类被调函数 |
| `0x1D2F418` | `B 0x1F27404` | 一条不同的尾调用分支 |
| `0x1D2F460` | `B 0x1D2EFEC` | 另一条尾调用分支 |
| `0x1D2F498` | `RET` | 有独立返回位置 |

注意：此为**有限的静态代码窗口**；这些地址不自动等同于
API 网络发送、注册 DTO 序列化、成功码或账户创建。尤其
`0x1D35CC8` 和 `0x1F27198` 需要通过原版 `script.json` 的准确函数入口
和控制流继续核对。

后续实机取证，应优先观察注册管理器入口及
`0x1D2F1F8` 尾调用目标的原生函数命中，再追相同事务的请求对象、
`SerializeRequestParameter`、`CallAfterResponse` 及 Token/Login，
不应再把 `0x1D2FA20` 的条件回调混入主链。

原版确认所需的照片、图像和账号真实 ID 应只保留在私人设备，
不能通过公开 GitHub Actions 上传。
