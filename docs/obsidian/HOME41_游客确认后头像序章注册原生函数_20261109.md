## 正确的动态验收

按同一原始客户端实例跟踪：

`ConfirmGestAccountSecond → DecisionGestAccount → b__84_6 → GoToPhase / SelectTrainerIcon / PlayPrologue / ApiManagerLogin.AtuhRegisterUser → request serializer → registration callback → token/login → UDManager.SetBasic`

上述箭头表示**需要动态验证的候选关系**，不是已证实调用图。另须记录 `GoToPhase` 的实际阶段编号，区分阶段请求与真实 View 初始化：

- 头像：`SelectTrainerIcon`、`_AddIconSelecter`、`SetData/CreateImages`，必要时本地私有截图辅助；`OnTapIcon` 仅表示原版按钮交互入口。
- 初始宝可梦：`PlayPrologue/2`、`FirstBootProloguePokemonPanel.Open`、`OnTapPokemon` 与本地 UI。只有独立核对具体选中种类，才能确认选中小火龙。
- 注册：`ApiManagerLogin.AtuhRegisterUser` 是注册管理器入口，后续序列化和回调均需另行证明。钩子计数为零时必须首先核对安装覆盖情况，不能直接断言后端没有请求。
- 账户持久性：完整用户可保留 userdata 的 Android 上的原版 HOME UI 六位 ID 对账、退出后冷启动同号。

实际代码：`969981/Home_Android/master/ci/home41_arm64_auth_timeline.js`、`ci/home41_arm64_auth_timeline.py`。这些 Hook 只读取入口计数和固定事件名称，不取得或导出 Token、UTID、原始响应或账号资料。

## 2026-11-09：从原始 Android APK 字节核验游客分支直接跳转

本轮不再只是方法名推断。原版 APK 已从用户 Library 中单独读取，并在本地解出
`lib/arm64-v8a/libil2cpp.so`。实际核对 SHA-256：

| 校验对象 | SHA-256 |
|---|---|
| 原版 HOME 4.1.0 APK（versionCode 81） | `8dee598028cd70441f645c8fff96b093b76778d625cdf07c60109eced50ffac1` |
| 原版 Android ARM64 `libil2cpp.so` | `80bfbc3d480bf3c91297d65a441a37e40260b70fd8b0ddc8da70c34f0870b6fe` |

根据原始 AArch64 ELF64 可执行 `PT_LOAD` 映射和原始指令字重算目标（不是伪代码推测），共有八个直接分支通过核验；下表列出最关键的五条：

| 原始指令 PC | 类型 | 精确目标 | 依据 |
|---|---|---|---|
| `0x1DE53DC` | `BL` | `0x1DEB3C0` | `ConfirmGestAccountSecond` 调用原始内部 helper，仍需确认其完整对象身份 |
| `0x1DEB4A4` | `B` | `0x1DE5508` | 第二层游客弹窗相关的正向回调跳板 → `DecisionGestAccount` |
| `0x1DEB58C` | `B` | `0x1DE5698` | 第二层游客弹窗相关的否定回调跳板 → `DenialGestAccount` |
| `0x1DE5690` | `B` | `0x1D2F8DC` | `DecisionGestAccount` 内部尾跳转 → `ApiManagerLogin.AtuhRegisterUser` |
| `0x1DE64D0` | `B` | `0x1DE1C10` | `b__84_6(bool isGestStart)` → `FirstBootBodyController.GoToPhase` |

注意：`B` 是尾调用，**仅扫描 `BL` 会漏掉 `DecisionGestAccount → AtuhRegisterUser`**。
正向/否定跳板的真实字节和静态目标已经验证，但其与用户实际按下的
「以游客身份开始使用」或「关闭」按钮之间的委托实例/调用时序，仍必须运行时验证，
不能将此静态关系写成已经真正点击或已经创建服务器账号。

### `b__84_6` 的完整五指令窗口

~~~asm
0x1DE64C0  MOV  W8, #7
0x1DE64C4  TST  W1, #1
0x1DE64C8  MOV  W9, #14
0x1DE64CC  CSEL W1, W9, W8, NE
0x1DE64D0  B    0x1DE1C10  ; FirstBootBodyController.GoToPhase
~~~

`isGestStart = true` 对应 `GoToPhase(14)`，即 `MT_LOGIN`；
`isGestStart = false` 对应 `GoToPhase(7)`，即 `NA_LINK_CONTINUE`。
这段回调只直接跳转 FirstBoot 阶段，**它本身不是服务器注册调用**。
尚未证明这段回调在第二次游客确认之后实际执行。

### 游客决定的状态写入

在 `DecisionGestAccount` 有 `0x1DE55F4 STRB W8,[X19,#0x139]`，
原始 opcode `0x3904E668`。匹配原始 `FirstBootBodyController._isDecisionGest`
偏移 `+0x139`；该函数接着进入内部准备逻辑，并可能在
`0x1DE5690` 通过 `B` 跳转注册管理器。
动态侧仍需要确认该实际基本块是否执行以及 API 返回后怎样进入下一阶段。
